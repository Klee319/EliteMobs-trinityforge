# 「何すりゃ良いか分からん」への対処案（2026-07-30）

- **発端**: プレイヤークレーム「要素が多すぎる／何をすれば良いか分からない／wikiを見ろにも程がある」
- **結論**: 要素数そのものより **①次の一手が示されない ②見ても意味が分からない ③情報がゲーム外にある** の3点が原因。
  いずれも**既存の機構（config）でかなり潰せる**。Java 改修が要るのは1点だけ（§P5）
- **併せて**: 私が出した追加コンテンツ案（`CONTENT_SPEC_...md`）は量が多いので、**投入の推奨を B案67種 → A案21種＋段階導入**へ下げる（§4）

---

## 1. 診断

| 症状 | 実際の原因 | 根拠 |
|---|---|---|
| 「何をすれば良いか分からない」 | **目標を提示する面がゲーム内に無い**。メニュー（スキルツリー/図鑑/カタログ）は最初から全部見えるが、順番が無い | TF の player 向けコマンドは `/tf collection` `/tf stats` `/tf role` `/tf bind` `/tf settings` のみ。「次にやること」を出す機構が無い |
| 「見ても意味が分からない」 | **ステータスの効果・トリガ・上限がゲーム内のどこにも無い**。`stats/lore.yml` は名前と書式だけ。唯一の説明文は config-editor の `labels.js` の自由文で**ゲーム内非表示・実装と未接続** | `ACTIVE_RECORD.md` K-5（既に「実装とズレている箇所5件」まで特定済み） |
| 「wiki見ろにも程がある」 | 情報がプレイ中に参照できない場所（外部wiki）にしか無い | — |
| 「要素が多すぎる」 | 20スレッド・6段の結晶・素材5種…を**同時に見せている**。系統名で束ねていないので個数がそのまま認知負荷になる | 本リポジトリの提案（§4で修正） |

**要点**: 「量を減らす」より先に **「順番を1本にする」「説明を持ち物に書く」「未解放を見せない」** の3つが効く。

## 2. 処方（優先順）

### P1. EliteMobs のクエストチェーンで導線を1本にする（★最優先・config のみ）

EliteMobs のクエスト機構が**そのまま使える**。すでに upstream が同じ形で導入クエストを出荷している
（`ag_welcome_quest_0.yml` / `ag_welcome_quest_1.yml`）。

使える部品（`CustomQuestsConfigFields` 実測）:

| フィールド | 用途 |
|---|---|
| `questName` / `questLore` / `questAcceptDialog` / `questCompleteDialog` | 何をすれば良いかを**日本語の会話で**説明する |
| 目的タイプ: `DIALOG` / `CustomKillObjective` / `CustomFetchObjective` / `KillObjective` / `ArenaObjective` | 「NPCと話す」「◯◯を倒す」「◯◯を納品する」を組める |
| `questLevel` | レベル帯で出し分け |
| `questAcceptPermission(s)` | **前提クエスト（チェーン）の実現**。前のクエスト完了で権限を付与する |
| `questCompleteCommands` | 次の章の解放・アイテム付与・メッセージ |
| `questLockoutPermission` / `questLockoutMinutes` | 一度きり／周回の切り替え |
| `setTurnInNPC` | 納品先NPC |

さらに **`QuestTracking` がスコアボードに現在の目標を常時表示する**。
これが「何すりゃ良いか分からん」への直接の答えになる（常時画面に出ているものは読まれる）。

> **権限プラグインが無い場合**: `questAcceptPermissions` の代わりに
> **前章の報酬アイテムを `CustomFetchObjective` の要求にする**ことで順序を作れる（config のみで完結）。

### P2. アイテムの lore に「これは何に使うか」を1行書く（★今日できる・効果大）

`items/catalog.yml` の `lore` は自由文（MiniMessage）で、**自動生成される品質行・ステ行より前に差し込まれる**。
素材・券・鍵にこれが無いのが「wiki見ろ」の直接原因なので、全アイテムに**用途1行**を入れる。

```yaml
  aether_dust:
    lore:
      - "<gray><i>高位の魔物が纏う魔力の残滓。</i></gray>"
      - ""
      - "<yellow>用途:</yellow> <white>ソース結晶の儀式に使う</white>"     # ← これ
      - "<dark_gray>入手: Lv65以上の魔物</dark_gray>"                      # ← これ
```

**書式を統一する**（読む側が学習できる）:

| 行 | 内容 |
|---|---|
| 1行目 | フレーバー（斜体グレー） |
| 空行 | — |
| `用途:` | 何に変わるか／何に使うか（1行） |
| `入手:` | どこから出るか（1行） |

### P3. 図鑑（`/tf collection`）を「やることリスト」として使う（config のみ）

現状の図鑑は「集めた記録」だが、**カテゴリの並び順を進行順にして、序盤の `reward-tiers` を密に置く**と
そのまま「次の目標一覧」になる。

- `categories.items.<id>.order` を **進行順**に振る（ソース入門 → 採取 → 反復ダンジョン → 束縛者）
- 序盤ティアのしきい値を**低く密に**（3件/6件/10件…）→ 「あと1個で報酬」が常に見える
- 報酬は称号・パーティクル・恒久QoL のみ（縦強化にしない＝憲法）

### P4. 未解放の要素を「見せない」（config のみ）

見えているのに触れない要素が認知負荷の大半。既存の解放機構を**徹底して使う**。

| 機構 | 対象 |
|---|---|
| `progression/crafting-features.yml` の `gated-catalog-recipes` | 上位結晶・鍵・エンド武器のレシピ（解放前は存在を見せない） |
| スキルツリーの `drop:<表>` | 採取のドロップ表（釣り/掘削/伐採の固有品） |
| スキルツリーの `trade:<職業>` | 村人の交換所（引換証の両替） |
| `dungeon/gates.yml` の `required-combat-level` | 上位ダンジョン |

**原則**: 序盤に見える要素は「戦う・掘る・釣る・ベリーを植える」の4つだけにする。

### P5. `/stats detail <key>` でステの意味をゲーム内に置く（★Java 小改修・根絶効果）

`ACTIVE_RECORD.md` K-5 の修正プランがそのまま答え。`stats/lore.yml` に
**トリガ（いつ効くか）・集計元（どの部位か）・上限**を構造化して持たせ、ゲーム内から読めるようにする。

```yaml
  dodge-chance:
    name: 回避率
    trigger:
      when: ON_DAMAGE_TAKEN
      sources: WORN_ARMOR
      applies-to: [MOB, PLAYER]
    limits:
      cap: 0.9
      cap-ref: "combat/damage.yml#defense.max-dodge-chance"
    text: "被弾時にこの確率でダメージを完全に回避する。上限90%。"
```

- 119キー全部を一度に埋めなくてよい。**戦闘系20キーから**（K-5 プラン §4 の推奨も先行検証）
- 副産物として「説明が実装からズレる」問題（K-5 の実測5件）も同時に解決する
- **これが入れば「wiki見ろ」を言わなくて済む**のが最大の価値

### P6. 数えるものを「束ねて名前を付ける」（設計の書き方の問題）

20個の個別名は覚えられないが、**5系統×4段**なら覚えられる。命名で系統が分かるようにする。

| 系統 | 命名の接尾/接頭 | 例 |
|---|---|---|
| 物理 | 「〜の刃/錐/楔」 | 鎧断ちの錐・秤の刃・天墜の楔 |
| 防御 | 「〜の帷/礎/残像」 | 静謐の帷・不動の礎・陽炎の残像 |
| 魔法 | 「〜の詠唱/環/遺稿」 | 星霜の詠唱・潮汐の環・古術士の遺稿 |
| 生産 | 「〜の手/見立て」 | 実りの手・名匠の見立て |
| 収集 | 「〜の指先/糸」 | 賭博師の指先・学びの糸 |

素材も同様に **帯素材3（Lv40/65/85）＋系統素材6** に整理し、名前で「どの帯か」が分かるようにする。

## 6. 【採用案】アチーブメント形式で進める

結論: **賛成。ただし TF のアチーブメント単体では成立しない**（一覧を見る面が無い）。
**バニラの進捗（advancement）画面を UI として借り、TF のアチーブメントを報酬エンジンにする**構成なら、
Java 改修ゼロで「一覧・ツリー・説明・進捗・達成通知」が全部揃う。

### 6-1. TF アチーブメントの実力と限界（実コード確認 2026-07-30）

| トリガ | 判定 | 何が書けるか | 制約 |
|---|---|---|---|
| `statistic` | Bukkit Statistic を **60秒ポーリング** | `MOB_KILLS` / `FISH_CAUGHT` / `PLAY_ONE_MINUTE` / `DAMAGE_DEALT` / `TRADED_WITH_VILLAGER` など | **qualifier 必須の統計は使えない**。`MINE_BLOCK` / `CRAFT_ITEM` / `KILL_ENTITY` / `PICKUP` は警告だけ出て**永久に発火しない**（`AchievementsConfig` が UNTYPED 以外を弾く） |
| `static`（図鑑） | 図鑑の登録状況を **60秒ポーリング** | 「このカタログ品を入手した」「この EntityType を倒した」「図鑑を N% 埋めた」「カテゴリを N 件埋めた」 | 入手判定は図鑑経由なので**最大60秒遅れる** |
| `advancement` | `PlayerAdvancementDoneEvent` で**即時** | バニラ／datapack の進捗キー一致 | 進捗の定義自体は datapack 側 |

- **1アチーブ = 1トリガのみ。前提条件（チェーン）のフィールドは無い** → 順序は「難易度で自然に並ぶ」だけ
- **一覧を見るコマンド/GUI が存在しない**（`/tf` は collection / stats / role / bind / settings / active / inspect …。achievements は無い）。
  現状の可視化は**達成時のチャット1行**と `broadcast` のみ
- 報酬は `special`（称号・パーティクル）/ `commands` / `items` / `job-exp` / `permanent-buffs` / `vanilla-exp`

**→ 単体だと「達成したことは分かるが、何を目指せば良いかは分からない」**。クレームの半分しか解決しない。

### 6-2. だから「バニラ進捗（advancement）」を UI にする

`AchievementListener` が `PlayerAdvancementDoneEvent` を拾って `achievements.yml` の `type: advancement` に
報酬を出す実装は**すでに入っている**。つまり datapack でカスタム進捗を定義すれば、そのまま報酬に繋がる。

バニラ進捗画面が最初から持っているもの:

| 欲しかったもの | バニラ進捗が提供 |
|---|---|
| 一覧UI | 進捗画面（既にゲーム内にある。専用コマンド不要） |
| 順序・前提条件 | `parent` によるツリー。**親を達成するまで子は霞んで見える**＝段階開示が自動 |
| 説明文 | 各進捗の `description`（日本語可）＝**wiki を見ずに済む本体** |
| 達成通知 | トースト表示＋チャット（`announce_to_chat`） |
| 分類 | タブ（ルート進捗ごとに1タブ） |
| 実装コスト | **Java 改修ゼロ**（datapack の JSON のみ） |

さらに **`statistic` の UNTYPED 制約を回避できる**のが大きい。
「石を100個掘る」は TF の `statistic` では書けない（`MINE_BLOCK` は qualifier 必須で弾かれる）が、
**advancement の `minecraft:mined_block` criteria なら書ける** → 達成したら TF が報酬を出す。
**掘削・伐採・クラフト系の実績は全部この経路にする。**

### 6-3. 役割分担（この構成なら EM クエストは必須でなくなる）

| レイヤー | 担当 | 置き場所 |
|---|---|---|
| **見せる面・順序・説明** | バニラ進捗ツリー（タブ5つ） | datapack（`data/<ns>/advancement/**.json`） |
| **報酬エンジン** | TF アチーブメント（`type: advancement`） | `progression/achievements.yml` |
| **収集の可視化** | 図鑑 GUI（既存） | `progression/collection.yml` |
| **称号・コスメ** | 特殊報酬 | `progression/special-rewards.yml` |
| （任意）最初の一本道 | EM クエスト1〜2本だけ（NPC会話でストーリー導入したい場合） | `plugins/EliteMobs/customquests/` |

§3 の「最初の60分」8章は、**そのまま進捗ツリーの第1タブ**に置き換えられる。

### 6-4. 進捗ツリーの構成案（タブ5つ・進捗24個）

```
[タブ1] はじめかた（root: 冒険の始まり）
 ├ 魔物を1体倒す                    → 称号なし・帯素材×3
 ├ スキルを1つ上げる                → SP1
 │  └ スキルノードを1つ開ける        → 帯素材×5
 ├ 採取で固有素材を手に入れる         → ガチャ券×1
 │  └ ガチャ券を使う                → スレッド×1（品質という概念の導入）
 ├ スレッドを防具にセットする         → 帯素材×5
 └ ダンジョンに1回入る               → 称号「新参」

[タブ2] 採取（root: 実りの道）
 ├ 石を100個掘る（mined_block）      ← statistic では書けない経路
 ├ 木を100本切る（mined_block）
 ├ 魚を50匹釣る（FISH_CAUGHT / statistic でも可）
 ├ 固有素材を3種そろえる（図鑑 static）
 └ 採取スレッドを1つ手に入れる        → 称号「稼ぐ者」

[タブ3] ソース経済（root: 魔力の循環）
 ├ ソースベリーを収穫する
 ├ ソースジャーに1000溜める
 ├ ソースの粒を作る                  → 称号「炉に薪をやる者」
 ├ ソース結晶を作る
 └ 濃縮結晶を作る                    → 称号「炉の主」

[タブ4] ダンジョン（root: 深部への道）
 ├ 反復ダンジョンを1回クリア
 ├ 属性テーマの異なる2つをクリア       → 「持ち替え」を教える進捗
 ├ combatレベル50に到達
 ├ 束縛者の鍵を作る
 └ 世界を繋ぐ者を倒す                → 称号「次元を縫う者」・broadcast

[タブ5] 収集（root: 記録する者）
 ├ 図鑑を10%埋める
 ├ 図鑑を25%埋める
 ├ 図鑑を50%埋める
 └ 図鑑を100%埋める                  → 称号「万物の記録者」
```

- **1タブ = 1つの遊び方**。プレイヤーは「今日はこのタブを進める」と決められる
- 進捗の `description` に**次の一手を命令形で**書く（「Lv65以上の魔物を狩れ。精気の塵が落ちる」）
- 報酬は F0 の時点では**既存アイテムと称号だけ**にする（新規アイテムを増やさない）

### 6-5. この案の弱点（正直な評価）

| 弱点 | 対処 |
|---|---|
| datapack は config-editor の管理外（エディタから編集できない） | リソースパックと同じ扱いで配布物として管理。JSON はテンプレ化すれば量産できる |
| 進捗の「◯/10」カウント表示は素直には出ない（advancement は criteria 全達成型） | 数量マイルストーンは `statistic` 型の TF アチーブに寄せる（`MOB_KILLS` 10/50/100 等）。進捗ツリー側は「1回やる」に留める |
| 説明文が datapack と TF lore の二重管理になる | **正は datapack の description**、アイテム lore は「用途/入手」1行だけ（§P2 の書式）に役割分担する |
| `static`（図鑑）型は最大60秒遅れる | 「作った瞬間に達成」させたい進捗は advancement の `inventory_changed`（`minecraft:custom_data` 判定）側で書く |
| カタログ品を advancement の条件にする書式は要検証 | 1.21 系は `predicates` / `components` で `minecraft:custom_data` を見られる想定。**実機で1件試してから量産**すること |
